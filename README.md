# G2 Peak View（仮称）

Even Realities G2 向けの山名・山稜ビュー。現在地から見える山稜と山の名前を、
向いている方向に合わせて G2 に表示する。

企画・引き継ぎ仕様は Notion の
[Even G2 山名・山稜ARビュー — アイディア・実装ハンドオフ](https://app.notion.com/p/3e61b0c05d9b81abbe4fe277ae2ec514)
にある。このリポジトリはその実装で、仕様の段階 A（山名コンパス）と B（山稜シルエット）の骨格、
C（頭の向きへの追従）は上下方向だけ。

## 使い方

```bash
npm install
npm test            # 35 件。ネットワーク不要
npm run typecheck
```

手元で山稜と見える山を確かめる（標高タイルを `.cache/dem/` に保存するので 2 回目以降は通信しない）:

```bash
npm run horizon -- --lat 35.6251 --lng 139.2436
```

ブラウザで画面を確かめる（G2 に送るのと同じビットマップを緑で表示する）:

```bash
npm run app:dev
```

`http://localhost:5177/?lat=35.6251&lng=139.2436` を開く。ボタンと ←→ キーでスワイプ、
スペースでタップ、スライダーで疑似ピッチ。

実機:

```bash
npm run app:dev     # dev サーバー（:5177、Tokyojihatsu の 5173/5175/5176 と被らない）
npm run app:qr      # 実機に読ませる QR
npm run app:pack    # dist/g2peakview.ehpk（約 100KB）
```

## 操作

| 入力 | 動作 |
|---|---|
| スワイプ | 向きを回す（既定 5°、メニューで 1° に） |
| タップ | 画面中央にいちばん近い山に向きをぴったり合わせる |
| ダブルタップ | 終了確認（審査要件）。診断画面では戻る |
| メニュー | 画角 60°/120°/30° ・ 上下追従 ・ 回転の刻み ・ 診断画面 ・ Gray4/Gray8 ・ 再計算 ・ 終了 |

**校正のしかた:** 起動すると、見える山のうちいちばん高い山の方向を向いた状態で始まる
（表示に「未校正」と出る）。知っている山を実際に正面に見て、スワイプでその山名を中央付近まで
持ってきてタップすると、向きがその山にぴったり合う。以後、首を回したぶんだけスワイプする。

## 左右の向きを手動にしている理由

SDK（0.0.15 / 0.0.16、型定義は同一）の IMU イベントは `x / y / z` の 3 値だけで、
Tokyojihatsu の実測で**重力加速度（単位 G）**だと分かっている。重力は首を左右に振っても
変わらないので、ここから北基準の方位（yaw）は原理的に出せない。メーカーは地磁気センサーの
搭載を説明しているが、SDK から読む手段は見当たらない。

- ポケットのスマホのコンパスは頭の向きではないので代わりにしない（仕様どおり）。
- 取れるようになったら `src/core/orientation.ts` の `HeadPose` に `northReference: 'magnetic'`
  で入れれば、あとの投影はそのまま使える。
- 診断画面で IMU の各軸の振れ幅を出している。**その場で水平に 360° 回って振れ幅が増えなければ、
  yaw は取れていない**と実機で確定できる。

## 構成

```
src/core/          描画に依存しない計算。Node のテストとアプリの両方が呼ぶ
├─ geodesy.ts      方位・距離・仰角。観測点に合わせた球（WGS84 と 0.02° 以内で一致）
├─ dem.ts          標高タイルの復号・タイル座標・距離帯・双一次補間
├─ demload.ts      必要なタイルを並列取得して詰める（取得手段は外から渡す）
├─ horizon.ts      山稜の計算と山頂の可視判定
├─ peaks.ts        山頂データの型と CSV の読み込み
├─ orientation.ts  頭の向き（手動 yaw ＋ IMU ピッチ）
├─ scene.ts        投影と山名の配置（表示リストを作るだけ・描かない）
├─ render.ts       表示リスト → ビットマップ
└─ bitmap.ts       Tokyojihatsu から複製（元は変更していない）
app/               G2 プラグイン
├─ app.json        マニフェスト（位置情報・cyberjapandata.gsi.go.jp）
└─ src/
   ├─ main.ts      画面・入力・起動
   ├─ display.ts   画像送信（最新フレーム優先・同じ絵は送らない・送信時間の記録）
   ├─ text.ts      山名のラスタライズ（canvas）
   └─ events.ts    入力判定
scripts/
├─ build-peaks.ts  data/raw/1003zan20260331.csv → src/data/peaks.json
└─ horizon-cli.ts  手元検証用
```

画面は 576×288。上の 576×144 が山稜（画像コンテナ 288×144 を左右 2 枚）、下が文字欄。

## 計算の中身

- **山稜:** 0.2° ごとの方位で、近くから遠くへ DEM をたどって見かけの仰角の最大を取る。
  刻みは DEM の画素間隔の 0.75 倍（細い尾根を飛び越えない。テストで確認）。
  足元 30m は見ない。
- **距離帯:** 0–6km は z13（約 16m/画素）、6–40km は z11、40–150km は z9。
  高尾山で 75 枚・7.5MB・取得 0.2〜0.5 秒、計算 0.7 秒（Mac の Node）。
- **地球の丸み:** 球の厳密式。100km 先で約 0.45° 下がる。**大気差は補正していない**（係数 0）。
- **高さの基準:** 観測点は DEM の地表高＋目の高さ 1.6m。GPS の高度は使わない
  （楕円体高と標高を混ぜないため）。展望台や建物の上では合わない。
- **可視判定:** 山頂より手前の地形だけと比べる。境界付近は DEM 誤差ぶん「不確か」にする。
  樹木・建物・雲は考えない。
- **無効値:** 海やタイル欠けは 0m で埋めずに「無し」として扱う。
- **表示名:** 同じ索引番号に複数の頂がある山だけ頂名（蛭ヶ岳・塔ノ岳）、それ以外は山名
  （富士山＜剣ヶ峯＞ は「富士山」）。

## 確認済み／未確認

**確認済み（手元・ブラウザ）**

- 高尾山山頂で、富士山が 238.1° SW・55km・可視、地表高 595m（実際の山頂 599m）。
- ブラウザで、富士山の山名が山稜のピークに乗る。スワイプ・タップ・画角切替・疑似ピッチが効く。
- `.ehpk` が作れる（約 99KB）。

**実機で未確認（次にやること）**

1. 画像 2 枚の送信にかかる時間。スワイプに追従できるか（診断画面の「送信」に出る）。
2. Gray4 と Gray8 のどちらが通るか、ニブルの並びが合っているか（縞に見えたら逆）。
   Tokyojihatsu の mapprobe でも未測定。
3. スワイプの向き（`SCROLL_TOP` / `SCROLL_BOTTOM` のどちらが右回りか）。逆なら
   `app/src/main.ts` の `TURN_ON_SCROLL_DOWN` を反転する。
4. IMU で yaw が取れないことの確定（診断画面で水平 360° 回転）。
5. G2 の光学的な視野角。画角 30° は仮値で、景色と見比べて決める。上下の位置合わせ
   （`verticalOffsetPx`）も同様。
6. 山名の文字が 2 値化後に読めるか。屋外でどれだけ視界を塞ぐか。
7. WebView 内での標高タイル取得（CORS は `*` を確認済み）と計算時間。スマホでは Mac より遅い。
8. ロック中の動作（Tokyojihatsu の知見では Beta build でしか試せない）。
